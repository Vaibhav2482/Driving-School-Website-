## Made during Phase 1

**Package versions (verified on 2026-09-20).**
Prisma is pinned to **7.10.0**: npm's `latest` tag for the `prisma` CLI points to a release candidate
(`8.0.0-rc.*`) while `@prisma/client` is at 7.10.0. TypeScript is **6.0.x** because typescript-eslint
requires `<6.1`. React Router is **7.x**: v8 was just released and unverified.
`bcrypt` is used (native) as suggested; fall back to `bcryptjs` if a native build ever fails on a host.

**Prisma 7 specifics.** The generated client lives in `server/src/generated/prisma` (git-ignored,
created by `postinstall`/`prisma generate`). Prisma 7 requires a driver adapter (`@prisma/adapter-pg`) and
no longer loads `.env` itself, so `prisma.config.ts` calls `dotenv`. The connection URL is attached to the
Prisma config only when `DATABASE_URL` is set, so `generate`/`validate` work without a database.

**ESM everywhere on the server** (`"type": "module"`, `NodeNext`), so relative imports carry `.js`
extensions. Development uses `tsx`; production runs `tsc` output with `node dist/server.js`.

**Dependency injection over singletons.** `createApp({ env, logger, prisma })`. Tests build an app with a
stub database and never read `.env`.

**Health has two endpoints.** `/api/v1/health` is liveness and never touches the database.
`/api/v1/health/ready` checks the database and returns 503 in the standard envelope if it is down.

**No repository layer.** Prisma is the data-access layer; services call it directly.

**UUIDv7 primary keys**, generated by Prisma (`uuid(7)`), so the schema does not depend on PostgreSQL 18's
native `uuidv7()` and works on 16+.

**Money = integer paise.** Formatting happens only at the UI edge (`formatInr`).

**User has `fullName`; Student/Instructor do not.** Avoids two sources of truth for a person's name.
`email` and `phone` are both optional but one is required (CHECK). Phone is the primary identifier for
most students; email is optional.

**Enquiry, Enrollment, Skill, Branch, RtaRequest, AuthToken, AuditLog were added** to the entity list in the
brief because the customer journey needs them (see [erd.md](erd.md)). `Enrollment` snapshots price so package
edits cannot alter history; lessons remaining and balances are derived, not stored.

**"Partial" payment is an enrollment balance state, not a payment status.** `Payment.status` is
`PENDING/PAID/FAILED/REFUNDED`.

**Double-booking is enforced by PostgreSQL exclusion constraints**, in a hand-written migration, on top of
application checks. `btree_gist` is required (it is a trusted extension).

**Composite foreign keys keep `studentId` consistent** on `Booking`, `Lesson` and `Payment`.

**The card address belongs to the Kondapur branch** (confirmed by the project owner in Phase 2). It is seeded both
as the business-level `business.address` setting and as the Kondapur branch address. The Hafeezpet address is unknown
and stays empty; the website shows "Address coming soon" for it until the owner adds one.

**"Recognised by Govt. of Telangana"** is seeded exactly as printed on the card. Confirm the supporting
registration/certificate before featuring it prominently, and do not embellish it.

**Client dev proxy.** Vite proxies `/api` to Express so development is same-origin (no CORS, cookies behave
as in production). Production is intended to be same-origin behind a reverse proxy too.

**Auth design (Phase 3).**

- _Access tokens are checked against the session on every request._ A pure JWT would stay valid for 15 minutes
  after sign-out or a detected token theft. One indexed lookup per request buys instant revocation.
- _A wrong current password on `change-password` is a 400 validation error, not a 401_, so the web app's
  "401 means the session ended" rule can never sign someone out for a typo.
- _The session is restored lazily._ Opening a public page does not call the API; the first protected page (or the
  sign-in page) asks the server whether the refresh cookie is valid.
- _The IP rate limiter counts failed attempts only_, so shared school Wi-Fi is not locked out by normal use. The
  trade-off (a determined attacker can lock a shared IP for the window) is accepted; account lockout is per
  account, separately.
- _No schema change_ was needed: Phase 1's `User`, `RefreshToken`, `AuthToken`, `Notification` and `AuditLog` already
  covered everything.
- _The Phase 1 development auth bypass (`VITE_DEV_BYPASS_AUTH_GUARDS`) has been removed completely._ Guards now
  depend only on a real session.

**Visual identity: "midnight & champagne" (public site redesign).** Deep navy from the client's card stays as the
structural colour; the red accent was replaced by champagne gold for calls to action, eyebrows and hairlines (red
remains only in the logo mark). Headings use Playfair Display (serif), body text Inter. The palette is defined once
in `client/src/styles/index.css`, so every page, including the admin/student/instructor shells, inherits it. Gold
_text_ on light backgrounds uses `accent-700` (5:1 contrast); `accent-600` is for lines, icons and focus rings only.
Photography comes from `client/src/config/photos.ts` and is **stock** (Unsplash licence): it is decorative, carries no
captions claiming it shows the school's cars, instructors or learners, and is meant to be replaced by the school's
own photos. The hero deliberately makes no statistical claims (ratings, pass rates, student counts) because none are
confirmed.

**Test quirk.** Under Vitest, `react-router` and `react-router/dom` resolve to different builds (CJS vs
ESM), producing two router contexts. Router tests therefore import `RouterProvider` from `react-router`;
the app uses `react-router/dom`. This is a test-runner artefact only.

**Design-system page is dev-only** (`/dev/design-system`), excluded from production builds.

**Rate limiting** uses the in-memory store (single API process). Per-endpoint stricter limiters (login,
password reset, enquiry) are built from `createRateLimiter` in the phases that add those endpoints.

## Made during Phase 2

**Dedicated dev port.** The client dev server uses port 5273 with `strictPort`, because other projects on the same
machine use 5173-5199. Vite fails loudly instead of silently taking a port that belongs to someone else.

**Public API uses slugs, not ids.** The enquiry form selects a package/branch by slug, and public endpoints expose no
internal ids, timestamps or status fields (enforced by `select` allow-lists and tested).

**Honeypot answers "success".** A submission with the hidden field filled returns the normal 201 but stores nothing, so bots
learn nothing. It is checked after rate limiting and before validation, so bots also count against the limit.

**Stale package on an enquiry is dropped, not rejected.** If a visitor picked a plan that has since been archived, the enquiry
is still saved without the plan: losing a lead is worse than losing a preference.

**No schema change.** The existing Package, Branch, BusinessSetting, RtaService, Review and Enquiry models were enough. The
enquiry's IP address is deliberately not stored.

**Crawler files come from the API.** `/robots.txt` and `/sitemap.xml` are generated from `CLIENT_URL` and the database, so no
domain is hard-coded and package pages appear automatically. The production reverse proxy must route these two paths to the API.

**Business-card fallback in the client.** `config/business-defaults.ts` duplicates the confirmed facts, but only as a fallback
while settings load or the API is unreachable. The API always wins once it answers. This trades a small duplication for never
losing the call and WhatsApp actions.

**Form focus is handled explicitly.** After a failed submit the first `aria-invalid` control (in page order) gets focus. React Hook
Form's built-in focusing picked the wrong field with the React 19 ref-as-prop pattern.

**Enquiry is not a booking.** The site says so wherever the form appears; a lesson is confirmed only after staff speak to the visitor.

## Pivot to a static single-page site (2026-09)

The backend (Express, Prisma/PostgreSQL, authentication, admin/student/instructor portals, booking and payments
plans) was removed. The client needs a marketing website, not a platform. **This supersedes every earlier entry in
this file about the server, database, roles, authentication, the public API, honeypot/rate limiting, crawler
files served by the API, and the multi-phase roadmap**; those are kept above only as history.

- **Enquiries go through WhatsApp click-to-chat**, not a stored lead. The trade-off: no lead database and no
  spam protection are needed, but enquiries are not recorded anywhere except in the school's WhatsApp.
- **Content is code.** Edit `content.ts` / `business-defaults.ts` and redeploy.
- **Old URLs redirect** to the matching section so shared links keep working.
- **Still true:** English only; no fake production data; no unconfirmed claims (ratings, pass rates, counts);
  stock photos are decoration and are never captioned as the school's own.

## Visual identity: "racing" (2026-09, supersedes "obsidian & gold")

The client rejected the dark gold theme. The site is now bright and motorsport-styled: carbon black (`brand`), racing red
(`accent`), cool silver neutrals (`sand`), Barlow Condensed slanted uppercase headings and Barlow body text. Primary
buttons have slanted ends; the hero photo is cut on a diagonal with a red and a carbon stripe. The logo is a red
sports-car outline with speed streaks (`components/site/Logo.tsx`, plus `public/favicon.svg`,
`public/apple-touch-icon.png` and `public/og-image.jpg`). It is a temporary mark: replace it via `brandLogo` when the
client supplies theirs. Palette tokens live in `client/src/styles/index.css`.
